Abstract

Managing personal money with notebooks or scattered spreadsheets is slow, error-prone and gives no real picture of spending habits. ExpenseTracker is a web application built on the MERN stack (MongoDB, Express.js, React.js, Node.js) that lets a user record income and expenses, organise them into categories, set monthly budgets, track savings goals, automate recurring payments and understand spending through interactive charts and monthly reports.

The system exposes a REST API secured with JWT authentication, uses a Redux Toolkit powered React front end, and stores data in MongoDB. Beyond basic CRUD it provides smart de-duplicated notifications, month-over-month reporting with percentage change, CSV export, receipt uploads, tags, favorites, light/dark mode and eight selectable colour themes. All data is strictly per-user and every amount is validated on both the client and the server. The project runs entirely locally with two commands and depends on no third-party services.

1. Introduction

1.1 Background

Most people know roughly what they earn but not where it goes. Tracking every expense by hand is tedious, and existing apps are often cluttered, ad-driven or locked behind subscriptions. A simple, private, self-hosted tracker solves this for students and individuals.

1.2 Problem Statement

There is a need for a lightweight web application that lets a user record transactions quickly, stay within monthly budgets, work towards savings goals, and see clear analytics — without relying on third-party services or internet connectivity beyond the local machine.

1.3 Proposed Solution

ExpenseTracker provides a single dashboard for all of this. Users register, add categories and transactions, set per-category monthly budgets, create savings goals and recurring expenses, and view analytics and monthly reports. Recurring items post themselves when due, notifications warn before budgets break, and every screen offers search, filters and export.

1.4 Scope

In scope: authentication, transaction management, categories, budgets, savings goals, recurring expenses, analytics, monthly reports, notifications, CSV export, receipt upload and appearance customisation (themes + dark mode). Out of scope: bank integration, multi-user shared accounts and native mobile apps — these are listed under Future Scope.

2. Objectives

  1. Build a full-stack application covering the complete finance workflow: transactions → budgets → goals → reports.
  2. Provide secure user accounts where each user can only access their own data.
  3. Give meaningful insight through interactive charts and month-over-month comparison.
  4. Warn users automatically when budgets are nearly or fully used, without repeating the same warning.
  5. Offer a clean, consistent and accessible interface with light/dark mode and selectable themes.
  6. Validate every amount on both ends so bad data can never reach the database.
  7. Keep the code simple and modular: small single-purpose files and sequential async/await flow that is easy to explain and maintain.

4. System Design

4.1 Architecture

ExpenseTracker follows a three-tier client–server architecture: a React single-page application (presentation), an Express REST API (application) and MongoDB (data). No page ever talks to the database directly — every read or write passes through the API, which authenticates the token and scopes the query to that user.

Data flow: Page → Redux slice → services/api.js (Axios + JWT header) → Express route → middleware (protect) → controller → Mongoose model → MongoDB → JSON response → slice state → UI and charts.

4.2 Request Lifecycle

  1. Client sends Authorization: Bearer <token> (attached automatically by the Axios request interceptor).
  2. protect middleware verifies the JWT and loads req.user.
  3. Controller validates/sanitises input (for example toAmount), then runs the query with user: req.user._id.
  4. Response returns a standardised { success, data/message } envelope.
  5. On HTTP 401 the Axios response interceptor clears the token and redirects to /login.
  6. Any thrown error lands in the central error handler, which maps CastError → 404, duplicate key → 400, Mongoose ValidationError → 400.

9. Implementation Highlights

9.1 Recurring Auto-Posting

When the app loads, every active recurring item whose nextDate is today or earlier is converted into a real transaction, its next due date is advanced by one frequency step, and a notification is created. The posted transaction keeps a link back to its recurring parent so the UI can mark it.

const dueItems = await RecurringExpense.find({
  user: userId, active: true, nextDate: { $lte: today },
});
for (const item of dueItems) {
  await Transaction.create({ user: userId, type: 'expense',
    amount: item.amount, category: item.category,
    description: item.title, date: item.nextDate,
    paymentMethod: item.paymentMethod, isRecurring: true,
    recurringExpense: item._id });
  item.nextDate = nextDateAfter(item.nextDate, item.frequency);
  await item.save();
}

9.2 Smart Notifications with De-duplication

Each alert carries a stable key such as budget:2026:10:Food:warn. Before creating a notification the server checks whether that key already exists, so the same warning never repeats inside a month — the bell stays useful instead of noisy.

const createOnce = async (userId, type, title, message, key) => {
  const alreadySent = await Notification.findOne({ user: userId, key });
  if (alreadySent) return;
  await Notification.create({ user: userId, type, title, message, key });
};

The budget checker calls it at ≥80% ("used 84%") and ≥100% ("over by 12%"), goals fire once when fully funded, and recurring items confirm each posting.

9.3 Budget Status Calculation

For each month the server loads the user's budgets, then aggregates that category's expenses inside the same month window ($match on user, type, category and date range, then $group with $sum). Percentage, remaining amount and status are derived and returned together, so the dashboard, budgets page and reports all read one source of truth.

9.4 Dashboard & Report Aggregation

Totals, six-month series and category breakdowns are computed with MongoDB aggregation pipelines executed with sequential await calls for readability. A notable bug was fixed here: inside $group, non-_id fields must be accumulated — bare paths raise "The field must be an accumulator object" — so fields like name and type use { $first: '$field' }.

9.5 Amount Validation (client + server)

const toAmount = (value) => {
  const number = Number(value);
  if (!Number.isFinite(number) || number <= 0) return null;
  return Math.round(number * 100) / 100;   // 123.456 -> 123.46
};

The client's sanitizeAmountInput strips letters and minus signs while typing and caps the decimal places, and the server independently converts and rejects invalid values with HTTP 400 — so abc, -5 or a zero budget never reach the database.

9.6 Chart Selector

Analytics keeps the fetched data mounted and only swaps the chart component (Bar / Line / Area / Donut / Pie), so switching views is instant and never re-fetches.

9.7 CSV Export

GET /api/transactions/csv applies the same filters as the on-screen list and streams a text/csv response with a date-stamped filename, generated by a small buildCsv helper.

9.8 Axios Interceptors

One request interceptor attaches Bearer tokens from localStorage; one response interceptor reacts to 401 by clearing the token and bouncing the user to /login. There is exactly one HTTP client in the app, so auth behaviour is defined in one place.

10. Security & Validation

  1. Passwords are hashed with bcrypt (10 rounds) and never returned by the API.
  2. JWT with configurable expiry is sent as an Authorization: Bearer header; the Axios interceptor attaches it and clears it on failure.
  3. Ownership checks: every find, update and delete includes the logged-in user's id.
  4. Server-side validation through sanitize.js returns 400 with clear messages for invalid amounts, empty titles and bad enum values.
  5. helmet security headers and a CORS allow-list restricted to the client URL; morgan logs every request in development.
  6. Multer restricts receipt uploads to image MIME types up to 2 MB.
  7. A central error handler maps CastError → 404, duplicate key → 400, ValidationError → 400 and never leaks stack traces to the client.
  8. All environment variables are read in exactly two files (server/src/config/env.js, client/src/config/env.js); secrets stay in a git-ignored .env with a committed .env.example.

13. Limitations

  • Recurring expenses are posted only when the app is opened, not by a background scheduler.
  • The production build shows a chunk-size warning (>500 kB) because Recharts bundles all chart types in one bundle.
  • Only monthly frequency and a single currency per user are supported; no live exchange rates.
  • No automated test suite yet; testing was done manually and with API calls.
  • Receipt images are stored on local disk, not in the database or cloud storage.

14. Future Scope

  1. Cron scheduler (node-cron) to post recurring expenses without opening the app.
  2. Monthly report emails and budget-breach push/email alerts.
  3. Bank statement (CSV/OFX) import and receipt OCR for automatic entry.
  4. Smart features: automatic category suggestion, anomaly detection and month-end forecasting.
  5. Multi-currency support with daily exchange rates and shared/family budgets.
  6. PWA with offline mode and a React Native mobile app using the same REST API.
  7. Rate limiting, refresh-token rotation and an audit log of edits/deletes.
  8. Jest + Supertest API tests, React Testing Library component tests, CI/CD pipeline.
  9. Route-level code splitting to remove the bundle-size warning.
  10. Gamification (streaks, savings badges) and chart image export for presentations.

15. Conclusion

ExpenseTracker delivers an end-to-end MERN application that covers the full personal-finance workflow — transactions, budgets, savings goals, recurring payments, analytics and reports — with secure per-user data, validation on both client and server, and a themeable, accessible interface built on a distinctive design system. The modular structure (small files, sequential async flow, centralised configuration and a single HTTP client) keeps the project easy to understand, maintain and demonstrate. The testing table and fixed-challenge log show a working, verified system, while the future-scope items provide a clear path for growth beyond the current semester's requirements.
